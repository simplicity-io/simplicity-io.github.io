AI Capability Check: Test methodology

Version 3 of the public methodology (suite version 3, app 0.3.9; updated 2026-11-12).

AI Capability Check measures a phone's on-device AI performance so that results can be checked and repeated. This document describes what is measured, how, and what the results do and do not show.

Overview

One run times fixed AI models on every processor the phone offers, checks that each processor's answers are correct, and turns the best correct times into one AI Capability Score and a level.

  • Tests, in groups: Recognition AI = photo recognition, object detection and sound recognition. Generative AI = image style, speech to text and a chat model (LLM). Extra = the heat test (not scored).
  • Optional parts: the chat model and speech to text run only if you downloaded them; the heat test can be switched off.
  • Processors: CPU, GPU and NPU, each measured separately. A processor counts only if its answers match the CPU's.
  • Also measured, not scored: an optional 2-minute sustained run (how much the phone slows when hot) and the phone's state (battery, temperature, charging).
  • Not scored: Google-managed AI features such as Gemini Nano. Google controls their versions, so they are shown beside the score, not in it.
  • Everything runs on the phone. Nothing is uploaded unless the user opts in.

Each test runs one to three models chosen in advance, using open licences and LiteRT-compatible files. Every phone runs the same set, so scores stay comparable.

Model choice: reliability first

Models are chosen for how reliably they finish and give correct answers on every reference phone, not for how impressive they are.

  • A new candidate model first runs as a trial: it is measured and reported, but not scored, until it finishes with matching answers on every reference device.
  • A model that keeps failing on some phones or processors is replaced rather than kept with exceptions. A failure on one processor alone (for example a compile time-out) falls back to the CPU and is fixed or dropped before the suite version is frozen.
  • Over time the suite narrows to the models with the best completion record.

Which phones are covered

The app aims to cover as many phones as possible. A phone is supported when its chipset and Android version are supported by the app and it completes more than 60% of the tests. A test counts as finished when it gives a time and correct answers, on the CPU at least. Each run reports its own completion rate: the share of the tests that were run which finished, and whether that exceeds 60%. Tests you left out (not downloaded, heat test switched off) are not counted. A skip for low memory or a time-out counts as not finished. A run that stops early because the phone is too hot (see below) counts neither for nor against the phone.

  • Minimum Android version: set by the system features the tests need, kept as low as possible to reach more phones.
  • Phone problems are shown, not hidden. When one phone of an otherwise working model fails because of the phone itself (a faulty driver, firmware or an overheating unit), the app adds no special workaround for it. It states what failed, why, and what still counts.
  • Phones that complete 60% or less are identified through the app's run reports and users' in-app problem reports. Before such a phone model is removed from the store's list of supported devices, a problem in the app is ruled out first.

Test inputs

All inputs ship with the app and are identical on every phone.

  • Classification photos: 14 public-domain or CC0 photos from Wikimedia Commons, centre-cropped to 224×224 lossless PNG. They were chosen from 41 candidates because both MobileNet versions recognise them with a clear margin.
  • Detection photos: 9 of those photos at 320×320, each showing a clear everyday object.
  • Chat model: a 256-token prompt for speed runs, plus three quiz questions with one correct answer each: the planets in order from the Sun, the capital of France, and 17 + 25.
  • Why not random noise: on random pixels every class scores almost the same, so tiny rounding differences change the answer and correct processors look wrong. Real photos have a clear answer.

Photo sources and licences are listed in the app's source repository.

Processors

Each model runs separately on every processor the phone offers, through Google's LiteRT runtime (LiteRT-LM for the chat model), with fixed settings so every phone runs the same way.

A processor is measured only if the phone reports it. LiteRT and NNAPI can quietly run work on the CPU instead. So any GPU, NPU or NNAPI result that is not at least 3% faster than the CPU is flagged "no speed-up" and never shown as a working accelerator. On Google Tensor phones, LiteRT's NPU route is skipped because Google limits that route to approved apps; the TPU is measured through NNAPI instead.

Timing

The reported time is the median of many timed runs on one fixed photo, after a warm-up.

  1. Load: the model is loaded and compiled for the processor. Load time is recorded separately and not scored.
  2. Warm-up: at least 10 runs and at least 1 s (CPU), 2 s (GPU) or 0.5 s (NPU), because processor clocks ramp up in the first second.
  3. Timed rounds: 5 rounds, each at least 50 runs and at least 1 s long. Every run includes reading back one output, because GPUs and NPUs can return before their work is done. Only the smallest output is read, so copying large outputs is not timed.
  4. Result: the median of all timed runs, plus the 90th percentile.
  5. Spread: how much the round medians differ, as a share of their median, leaving out the single fastest and slowest round. The full range is kept too. The target is 5% or less.
  6. Steadiness: a result whose spread is over 10% is labelled unsteady on this phone. Unsteady is not a failure: the score uses the median, which holds up when single rounds jump, and the completion rate ignores steadiness. Only wrong answers or a test that does not finish count as failures. For the chat model, the spread of answer speed across its three runs is used. Since app 0.3.10 a set of rounds that comes out unsteady is timed once more with the model still loaded, and the steadier set counts; if the lane that decides a test's score is still unsteady, that test's score is shown as approximate (≈).

Why results vary. CPUs are usually steady. GPUs vary most on short tests, because phones lower GPU clocks in the short gaps between photos and must raise them again. Some GPU drivers are unreliable and can swing widely or give wrong answers. Heat matters in long runs, which the sustained run measures. The app does not tune itself per phone, so every phone is measured the same way.

Why runs are not simply made longer. Each round already lasts at least 1 s and 50 runs. Longer rounds average more photos but do not remove the gaps between photos, which is where GPU clocks drop. They also heat the phone, which brings throttling in, and make users wait longer. Running photos back to back without reading each answer would hide the gap, but it would measure throughput rather than the time to answer one photo.

Chat model: LiteRT-LM's own benchmark reads a 256-token prompt and writes 64 tokens, three times per processor. The medians of prompt speed and answer speed (tokens per second), time to first token and load time are reported.

Every line of a run is also written to a log file on the phone, and the full report is saved as JSON.

Answer checks

A fast processor with wrong answers counts for nothing. After timing, each processor answers every test input once (untimed), and its answers are compared with the CPU running the same model.

TestA processor's results match the CPU when…
Image classificationits top answer equals the CPU's on at least 90% of the 14 photos, and is always among the CPU's top 5
Object detectionits best class equals the CPU's on at least 90% of the 9 photos, with the score within 0.15
Chat modelit answers at least as many of the 3 quiz questions correctly as the CPU (greedy decoding, model "thinking" off)

Wrong quiz answers. The quiz checks that a processor runs the model correctly, not how capable the model is. A small, 4-bit compressed model can get a question wrong on every processor. That is a limit of the model, so the CPU's own result is the yardstick and quiz answers are never scored on their own. A processor fails the check only when it gets fewer right than the CPU, which points to number-precision differences (GPUs often compute at half precision) or a driver problem.

The CPU itself is checked against reference answers computed on a PC with the same model files. This shows that photos are decoded identically on the phone.

A processor that fails shows "Results don't match" and is left out of the score.

Sound, speech and image style tests

Sound recognition. A sound classifier (YAMNet) listens to seven short public-domain clips (applause, speech, a car horn, a church bell, a crying baby, a siren and a thunderstorm) on every processor, with the same timing rules and answer check as the photo tests. It is scored and part of Recognition AI.

Speech to text. A small speech recognizer (Whisper tiny, downloaded on demand like the chat model) transcribes four short public-domain recordings on each processor. Two things are timed: the encoder, and how fast the text is written (word pieces per second). Each processor's transcripts must match the CPU's within 10 % (counted in word pieces), and a graphics processor that misses at half precision is retried at full precision. It is scored and part of Generative AI. While a processor writes its transcripts, the screen shows the words (at most about five redraws a second), and if you turn the speaker on, the next processor pass plays each recording and the test waits for it to finish before the next one (only the model's own work is timed, so results don't change). The sound test plays its clips the same way. The encoder is timed with the screen still.

Image style. A style transfer model (Magenta arbitrary image stylization, Apache 2.0) repaints four public-domain photos in the style of two public-domain paintings (The Starry Night by Van Gogh, The Great Wave by Hokusai), eight pictures in all. The style of each painting is prepared on a PC; the phone times the repainting network at 384x384 pixels with the same warm-up and rounds as the photo tests. Answers are compared by structural similarity (SSIM, 1 = identical, on grey copies): each processor must be at least 0.95 against the CPU on every picture, and the CPU at least 0.90 against the PC's reference. A graphics processor that misses at half precision is retried at full precision, and an accelerator that is not 3% faster than the CPU is flagged "no speed-up". It was a trial from app 0.1.68 and is scored since suite version 3 (app 0.3.9), part of Generative AI, after it finished with matching pictures on every reference phone.

The speech score combines the encoder time and the text-writing speed.

Sustained run and pre-run checks

Sustained run (heat test). Optional (a checkbox, off by default) and not scored. Last in every run, because it heats the phone on purpose. MobileNet V2 runs non-stop for 2 minutes on the fastest processor whose answers were correct. Every 10 seconds the app records photos per second, latency, battery temperature, the phone's thermal state and, where the phone reports it, live thermal headroom (1.0 means the phone starts slowing itself down). Android refreshes battery temperature only about once a minute, so the summary also keeps the battery temperature at the start and end. Sustained % is the speed in the last 30 seconds divided by the speed in the best 30 seconds of the run (from 0.1.37; before, the first 30 seconds, which let a slow start push it over 100 %). It is shown beside the score, never inside it.

Pre-run checks. Before a run the app records battery level, battery temperature, thermal state and power source, and warns about:

  • battery under 20% while not charging (some phones slow down)
  • battery over 40 °C (let the phone cool first)
  • the phone already limiting its own speed because of heat
  • charging (recorded, not a failure; results are compared only within the same power state)

Heat safety. Before a run the app shows a warning, until you tick "Don't show this again". During a run it checks between measurements (never inside a timed loop) whether Android reports a severe heat state or worse, or the battery is above 45 °C. If so, the run stops by itself and keeps the results so far. Such a run counts neither for nor against the phone's support, and its score (from the tests that finished) gets no level. Phones also protect themselves by slowing down; stopping earlier avoids stressing the battery.

On phones with less than 8 GB of memory, the chat model also needs free memory of at least 1.2× its file size, or it is skipped (larger phones always try, since Android counts cached apps as used memory), and each processor gets at most 15 minutes for it.

Scoring and levels

Every result shows the numeric AI Capability Score, for comparing, and one of five levels, for a quick read.

  1. Reference phone: a reference phone (a recent flagship) on battery scores 1000 on suite version 3. Every reference value is the median of the same three full runs on battery with the released app (2026-11-12), so each test is measured as you run it. Suite version 2 (app 0.1.66-0.3.8) took them from separate part runs on a cooler phone, so its scores are not comparable.
  2. Test score: for time-based tests, reference time ÷ your time × 1000 (twice as fast = 2000). For the chat model, your speed ÷ reference speed × 1000, averaging prompt and answer speed. Speech to text combines the encoder time and the text-writing speed (geometric mean), from the matching processor with the best combined result. Each test uses its best processor whose answers matched.
  3. Two halves: the Recognition score is the geometric mean of the three recognition test scores (photos, detection, sound). The Generative score is the geometric mean of image style, speech to text and chat (suite version 3; before, speech to text and chat).
  4. AI Capability Score: the geometric mean of the two halves, so each half counts 50% and one very fast test cannot hide a very slow one. Earlier app versions weighed the tests differently (before 0.1.66 the five tests counted equally; before 0.1.65 only photos, detection and chat counted), so those scores are not comparable.

In short, where each name stands for that test's score:

  • Recognition = ∛(photos × detection × sound)
  • Generative = ∛(image style × speech to text × chat)
  • AI Capability Score = √(Recognition × Generative)

Edge cases:

  • If a test cannot run (not enough memory, time-out), that test gets the floor score of 1 and the level is capped at the lowest two. A score of exactly 0 would make the whole geometric mean 0.
  • Downloads are optional. If you did not download the chat model or speech to text, that test does not run and the result is marked "partial": a score from the tests that ran (shown only when both halves have at least one test), but no level. A level needs every scored test. Tests you left out are not counted in the completion rate.
  • A processor marked "Results don't match" never counts. If no processor matches, that test gets the floor score of 1.
  • The heat test and Google-managed AI features are shown beside the score, not in it.

Levels: Basic (under 200), Capable (200-399), Advanced (400-799), Flagship (800-1599) and Cutting-edge (1600 or more): each level starts at twice the score of the one below. A capped result is at most Capable; partial results (a scored test left out) get no level.

Fairness rules and versioning

  • Same inputs everywhere: models, photos and prompts are fixed and pinned by SHA-256. Scores are compared only within the same suite version.
  • Nothing else runs during a test: no ads load or refresh and no network work happens until the run ends.
  • Same power state: results are compared only with runs in the same power state (on battery or charging). Since app 0.3.10 a score measured while charging (at the start or end of the run) is marked "Charging" next to the score, because the reference phone is measured on battery.
  • Honest fallbacks: a processor the phone does not offer is skipped, never scored. Suspected CPU fallbacks are flagged.
  • Model downloads: the optional chat and speech models are downloaded once, ahead of the run, and checked against its pinned SHA-256 before use.
  • New suite version: any change to models, inputs, settings, runtime versions (LiteRT, LiteRT-LM, Qualcomm QNN) or the formula raises the suite version, and the reference phone is measured again so that it scores 1000. Suite 3 runs on LiteRT 2.3.2, LiteRT-LM 0.18.0 and QNN 2.51.0; each score records its suite and runtimes.
