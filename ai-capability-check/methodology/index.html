OnDevice AI Meter: Test methodology

Version 3 of the public methodology (updated 2026-11-20 for suite version 5, app 1.1.14). The reference values are those of suite version 3 (app 0.3.9, 2026-11-12), except the chat model's, which was measured again for suite version 5 (Gemma 3 1B, 2026-11-18).

OnDevice AI Meter measures a phone's on-device AI performance so that results can be checked and repeated. This document describes what is measured, how, and what the results do and do not show.

Overview

One run times fixed AI models on every processor the phone offers, checks that each processor's answers are correct, and turns the best correct times into one AI Capability Score and a level.

  • Tests, in groups: Recognition AI = photo recognition, object detection and sound recognition. Generative AI = image style, speech to text and a chat model (LLM). Extra = the AI multitasking test (not scored).
  • Optional parts: the chat model and speech to text run only if you downloaded them; the AI multitasking test can be switched off.
  • Processors: CPU, GPU and NPU, each measured separately. A processor counts only if its answers match the CPU's.
  • Also measured, not scored: the AI multitasking test (about 3 to 5 minutes: longer on phones whose AI processor passes more steps; how much CPU work an accelerator takes off the CPU, and how many camera-like AI jobs the phone runs beside another job) and the phone's state (battery, temperature, charging).
  • Not scored: Google-managed AI features such as Gemini Nano. Google controls their versions, so they are shown beside the score, not in it.
  • The tests run on the phone, offline. Test results stay on it. Released versions send anonymous usage events and crash reports (Firebase) and show ads (Google AdMob) outside the tests; see the privacy policy.

Model choice: reliability first

Models are chosen for how reliably they finish and give correct answers on every reference phone, not for how impressive they are.

  • A new candidate model first runs as a trial: it is measured and reported, but not scored, until it finishes with matching answers on every reference device.
  • A model that keeps failing on some phones or processors is replaced rather than kept with exceptions. A failure on one processor alone (for example a compile time-out) falls back to the CPU and is fixed or dropped before the suite version is frozen.
  • Over time the suite narrows to the models with the best completion record.

Which phones are covered

The app aims to cover as many phones as possible. A phone is supported when its chipset and Android version are supported by the app and it completes more than 60% of the tests. A test counts as finished when it gives a time and correct answers, on the CPU at least. Each run reports its own completion rate: the share of the tests that were run which finished, and whether that exceeds 60%. Tests you left out (not downloaded, AI multitasking test switched off) are not counted. A skip for low memory or a time-out counts as not finished. A run that stops early because the phone is too hot (see below) counts neither for nor against the phone.

  • Minimum Android version: set by the system features the tests need, kept as low as possible to reach more phones.
  • Phone problems are shown, not hidden. When one phone of an otherwise working model fails because of the phone itself (a faulty driver, firmware or an overheating unit), the app adds no special workaround for it. It states what failed, why, and what still counts.
  • Phones that complete 60% or less are identified through the app's run reports and users' in-app problem reports. Before such a phone model is removed from the store's list of supported devices, a problem in the app is ruled out first.

Test inputs

All inputs ship with the app and are identical on every phone.

  • Classification photos: 14 public-domain or CC0 photos from Wikimedia Commons, centre-cropped to 224×224 lossless PNG. They were chosen from 41 candidates because both MobileNet versions recognise them with a clear margin.
  • Detection photos: 9 of those photos at 320×320, each showing a clear everyday object.
  • Chat model: a 256-token prompt for speed runs, plus three quiz questions with one correct answer each: the twelve months of the year in order (since app 1.1.6; before, the days of the week, which the Gemma chat model got wrong on every phone, and before app 1.0.8 the planets in order from the Sun, which the small chat model often got wrong on every phone), the capital of France, and 17 + 25.
  • Why not random noise: on random pixels every class scores almost the same, so tiny rounding differences change the answer and correct processors look wrong. Real photos have a clear answer.

Photo sources and licences are listed in the app's source repository.

Processors

Each model runs separately on every processor the phone offers, through Google's LiteRT runtime (LiteRT-LM for the chat model), with fixed settings so every phone runs the same way.

A processor is measured only if the phone reports it. LiteRT and NNAPI can quietly run work on the CPU instead. So any GPU, NPU or NNAPI result that is not at least 3% faster than the CPU is flagged "no speed-up" and never shown as a working accelerator. On Google Tensor phones, LiteRT's NPU route is skipped because Google limits that route to approved apps; the TPU is measured through NNAPI instead.

AI processor access differs by platform. Each chip maker decides how apps reach its NPU, and the app measures only what an ordinary app can reach: Snapdragon through Qualcomm's QNN libraries bundled with the app (most recent chips); Google Tensor through NNAPI (Google limits its direct LiteRT route to approved apps); Samsung Exynos through NNAPI where a vendor driver exists (about 2x the CPU on the Exynos 2400, no gain on the Exynos 1480, no driver on the 1330); MediaTek Dimensity 7300, 8300 and 9000 to 9500 through LiteRT with MediaTek NeuroPilot for the photo, object, sound, image style and speech tests (other MediaTek chips: NNAPI drivers gave no gain on the phones tried); entry-level chips usually have no NPU an app can reach. Large gaps between phones in the rankings therefore reflect both the chip and how open its NPU is to apps. Google's direct route to the Pixel TPU (the Tensor SDK, Tensor G5 and later) comes with a licence that does not allow publishing benchmark results, so the app doesn't use it: Pixel phones are measured through NNAPI, which may not reach the TPU's full speed, so Pixel AI processor results may understate the chip. See also the FAQ ("Why AI processors differ between phones") and in the app's result details.

Timing

The reported time is the median of many timed runs on one fixed photo, after a warm-up.

  1. Load: the model is loaded and compiled for the processor. Load time is recorded separately and not scored.
  2. Warm-up: at least 10 runs and at least 1 s (CPU), 2 s (GPU) or 0.5 s (NPU), because processor clocks ramp up in the first second.
  3. Timed rounds: 5 rounds, each at least 50 runs and at least 1 s long. Every run includes reading back one output, because GPUs and NPUs can return before their work is done. Only the smallest output is read, so copying large outputs is not timed.
  4. Result: the median of all timed runs, plus the 90th percentile.
  5. Spread: how much the round medians differ, as a share of their median, leaving out the single fastest and slowest round. The full range is kept too. The target is 5% or less.
  6. Steadiness: a result whose spread is over 10% is labelled unsteady on this phone. Unsteady is not a failure: the score uses the median, which holds up when single rounds jump, and the completion rate ignores steadiness. Only wrong answers or a test that does not finish count as failures. For the chat model, the spread of answer speed across its three runs is used. Since app 0.3.10 a set of rounds that comes out unsteady is timed once more with the model still loaded, and the steadier set counts; if the lane that decides a test's score is still unsteady, that test's score is shown as approximate (≈).

Why results vary. CPUs are usually steady. GPUs vary most on short tests, because phones lower GPU clocks in the short gaps between photos and must raise them again. Some GPU drivers are unreliable and can swing widely or give wrong answers. Heat matters in long runs; the app records the thermal state, but the score does not depend on it. The app does not tune itself per phone, so every phone is measured the same way.

Why runs are not simply made longer. Each round already lasts at least 1 s and 50 runs. Longer rounds average more photos but do not remove the gaps between photos, which is where GPU clocks drop. They also heat the phone, which brings throttling in, and make users wait longer. Running photos back to back without reading each answer would hide the gap, but it would measure throughput rather than the time to answer one photo.

Chat model: LiteRT-LM's own benchmark reads a 256-token prompt and writes 64 tokens, three times per processor. The medians of prompt speed and answer speed (tokens per second), time to first token and load time are reported.

Every line of a run is also written to a log file on the phone, and the full report is saved as JSON.

Answer checks

A fast processor with wrong answers counts for nothing. After timing, each processor answers every test input once (untimed), and its answers are compared with the CPU running the same model.

TestA processor's results match the CPU when…
Image classificationits top answer equals the CPU's on at least 90% of the 14 photos, and is always among the CPU's top 5
Object detectionits best class equals the CPU's on at least 90% of the 9 photos, with the score within 0.15
Chat modelit answers at least as many of the 3 quiz questions correctly as the CPU (greedy decoding, model "thinking" off)

Wrong quiz answers. The quiz checks that a processor runs the model correctly, not how capable the model is. A small, 4-bit compressed model can get a question wrong on every processor. That is a limit of the model, so the CPU's own result is the yardstick and quiz answers are never scored on their own. A processor fails the check only when it gets fewer right than the CPU, which points to number-precision differences (GPUs often compute at half precision) or a driver problem.

The CPU itself is checked against reference answers computed on a PC with the same model files. This shows that photos are decoded identically on the phone.

Why the CPU is the yardstick. The CPU is the one processor every phone has and every model runs on, and it runs the same model file with fixed, full-precision math through LiteRT's standard CPU path (XNNPACK), never a vendor driver. So it is the reference each GPU, NPU or NNAPI result is compared with. The CPU is not trusted blindly: its answers are themselves checked against reference answers computed on a PC (photos, objects, sounds, image style and speech), and the chat model answers a quiz with known answers. Agreement with the CPU is a consistency check within set tolerances, not proof of correctness: if the CPU and an accelerator made the same mistake, the check would not catch it, except where the PC reference or the quiz covers it. The tolerances are per test: top answer equal on at least 90% of inputs (photos, objects, sounds; object scores within 0.15), transcripts within 10% (word pieces), pictures at SSIM 0.95 or more, quiz at least as many right as the CPU. Float (FP32/FP16) and INT8 versions of a model are separate model files, each compared with the CPU running that same file; a graphics processor that misses at half precision (FP16) is retried at full precision (FP32).

Two kinds of check (named since app 0.3.10). Execution consistency: each GPU, NPU or NNAPI result is compared with the CPU running the same model, which shows that the processor ran the model correctly. Model output check: the CPU's answers are compared with reference answers from a PC (photos, objects, sounds, image style and speech), and the chat model answers a short quiz. Neither is a measure of how accurate a model is at its task: the score never rewards or penalises a model's accuracy, only the speed of processors whose answers are consistent.

A processor that fails shows "Results don't match" and is left out of the score.

Sound, speech and image style tests

Sound recognition. A sound classifier (YAMNet) listens to seven short public-domain clips (applause, speech, a car horn, a church bell, a crying baby, a siren and a thunderstorm) on every processor, with the same timing rules and answer check as the photo tests. It is scored and part of Recognition AI.

Speech to text. A small speech recognizer (Whisper tiny, downloaded on demand like the chat model) transcribes four short public-domain recordings on each processor. Two things are timed: the encoder, and how fast the text is written (word pieces per second). Each processor's transcripts must match the CPU's within 10 % (counted in word pieces), and a graphics processor that misses at half precision is retried at full precision. It is scored and part of Generative AI. While a processor writes its transcripts, the screen shows the words (at most about five redraws a second), and if you turn the speaker on, the next processor pass plays each recording and the test waits for it to finish before the next one (only the model's own work is timed, so results don't change). The sound test plays its clips the same way. The encoder is timed with the screen still. On Snapdragon AI processors only the INT8 Whisper runs (since app 1.1.6): they run the float model at half precision and its transcripts break down.

Image style. A style transfer model (Magenta arbitrary image stylization, Apache 2.0) repaints four public-domain photos in the style of two public-domain paintings (The Starry Night by Van Gogh, The Great Wave by Hokusai), eight pictures in all. The style of each painting is prepared on a PC; the phone times the repainting network at 384x384 pixels with the same warm-up and rounds as the photo tests. Answers are compared by structural similarity (SSIM, 1 = identical, on grey copies): each processor must be at least 0.95 against the CPU on every picture, and the CPU at least 0.90 against the PC's reference. A graphics processor that misses at half precision is retried at full precision, and an accelerator that is not 3% faster than the CPU is flagged "no speed-up". It was a trial from app 0.1.68 and is scored since suite version 3 (app 0.3.9), part of Generative AI, after it finished with matching pictures on every reference phone.

The speech score combines the encoder time and the text-writing speed.

AI multitasking test and pre-run checks

AI multitasking test. Goal. Phones run more and more AI all the time (camera effects, live captions, translation). When the AI or graphics processor does that work, the phone's other work keeps its speed. This test shows how well a phone runs AI next to everything else. On by default (a checkbox on the start screen; it can be unticked), about 3 to 5 minutes (longer on phones whose AI processor passes more steps), last in every run, never part of the score; its results are qualitative. It does not measure heat, battery, power or energy, and uses no non-public or vendor-specific APIs. It has two parts.

Part 1, AI offload (CPU work saved). MobileNet V2 runs at a fixed 30 photos per second, like a camera, for 1 minute on the CPU and then 1 minute on the fastest AI or graphics processor whose answers matched the CPU and that was faster than the CPU (NPU through Qualcomm or MediaTek libraries or through NNAPI with INT8; GPU with the float model). Both halves use the same model and the same work, so they compare like for like. The CPU half runs first, so the accelerator half starts on a slightly warmer phone; this favours the CPU, never the accelerator. Per half, the app measures its own CPU time per photo with Android's public Process.getElapsedCpuTime, minus the app's idle CPU time measured just before (5 s, screen held still). Work done on the accelerator itself is not CPU time, which is the point. CPU work saved = 1 - (accelerator CPU time per photo / CPU-lane CPU time per photo): how much less CPU time per photo the processor needs. If no accelerator gave matching answers, the result says that nothing takes work off the CPU. Nearly every phone with a usable accelerator saves 94-99%, so this part shows the gain, not the differences between phones.

Part 2, AI capacity. An ordinary non-AI job (data compression on all fast CPU cores but one, like a busy phone; the free core feeds the AI) runs alone for 8 seconds to get its baseline speed, measured again before every step so that heat building up doesn't count against later steps (since app 1.1.6; earlier versions used every fast core and one baseline). It then runs beside one camera-like AI job (object detection, EfficientDet-Lite0, 30 frames per second) on the CPU, for contrast, and then beside 1, 2, 4, 8, 16, 32 and 64 such jobs on the phone's fastest accelerator whose answers matched the CPU and that was faster than the CPU, 8 seconds each, until a step fails. A step passes when the AI keeps at least 95% of its frames on time and the other job keeps at least 80% of its speed. A step that fails is tried once more and the better try counts (since app 1.1.14), because a single 8-second window can tip a borderline phone either way; on some phones the accelerator's driver itself uses the fast CPU cores, which then shows as a lower share for the other job. The result is the number of camera-like AI jobs the phone handles and a level: Limited (0-1), OK (2-4), Good (8) or Excellent (16 or more). It separates strong, well-supported AI processors from older or poorly supported ones (some phones' accelerators are even slower than their CPU). A newer version of the test with a heavier job will follow when typical flagships reach the top step. The test is versioned separately from the score suite. If the AI processor can't run EfficientDet (the Pixel TPU through NNAPI can't compile it), the streams run the lighter MobileNet V2 INT8 on it instead, CPU contrast included, and the result says so (1.1.2).

Pre-run checks. Before a run the app records battery level, battery temperature, thermal state and power source, and warns about:

  • battery under 20% while not charging (some phones slow down)
  • battery over 40 °C (let the phone cool first)
  • the phone already limiting its own speed because of heat
  • charging (recorded, not a failure; results are compared only within the same power state)

Heat safety. Before a run the app shows a warning, until you tick "Don't show this again". It also says that running the tests is your choice and that the author can't be responsible for damage to your phone. During a run it checks between measurements (never inside a timed loop) how hot the phone is. If Android reports a "severe" heat state, or the battery is above 45 °C, the run pauses between tests for up to 3 minutes to let the phone cool, then goes on; tests that start while the phone is still that hot are marked "ran hot", and the run keeps its level. If Android reports a "critical" heat state or worse, or the battery is above 48 °C, the run stops by itself and keeps the results so far. Such a run counts neither for nor against the phone's support, and its score (from the tests that finished) gets no level. You can also stop a run yourself with the Stop button. Phones also protect themselves by slowing down. (Since app 1.0.5; before, the run stopped at "severe" or 45 °C.)

On phones with less than 8 GB of memory, the chat model also needs free memory of at least 1.2× its file size, or it is skipped (larger phones always try, since Android counts cached apps as used memory), and each processor gets at most 15 minutes for it. On those phones the chat model runs on the GPU only with free memory of at least 3.4× its file size. Since app 1.1.21 the chat model is not run on the Adreno 610 GPU (Snapdragon 662, 680 and similar): LiteRT-LM failed there every time.

Scoring and levels

Every result shows the numeric AI Capability Score, for comparing, and one of five levels, for a quick read.

  1. Reference phone: a reference phone (a recent flagship) on battery scores 1000 in every test, so 3000 per half and 6000 in total, on suite version 5. Every reference value is the median of three full runs on battery with the released app, so each test is measured as you run it: the same three runs for photos, detection, sound, image style and speech (suite version 3, 2026-11-12), and three later runs for the chat model (suite version 5, 2026-11-18). Suite version 2 (app 0.1.66-0.3.8) took them from separate part runs on a cooler phone, so its scores are not comparable.
  2. Test score: for time-based tests, reference time ÷ your time × 1000 (twice as fast = 2000). For the chat model, your speed ÷ reference speed × 1000, as the geometric mean of the prompt and answer speed ratios. Photo recognition takes the geometric mean of its two model families (MobileNet V2 and EfficientNet-Lite0). Speech to text combines the encoder time and the text-writing speed (geometric mean), from the matching processor with the best combined result. Each test uses its best processor whose answers matched.
  3. Two halves: the Recognition score is the sum of the three recognition test scores (photos, detection, sound). The Generative score is the sum of image style, speech to text and chat.
  4. AI Capability Score: the sum of the two halves (since app 0.3.18). Before, each half and the total were geometric means and the reference phone scored 1000; the app recomputes those earlier results as sums from their stored test scores, so your test history stays comparable. Before 0.1.66 the tests were weighed differently, so those scores are not comparable.

In short, where each name stands for that test's score:

  • Recognition = photos + detection + sound
  • Generative = image style + speech to text + chat
  • AI Capability Score = Recognition + Generative

Edge cases:

  • If a test cannot run (not enough memory, time-out), that test gets the floor score of 1 and the level is capped at the lowest two.
  • Downloads are optional. If you did not download the chat model or speech to text, that test does not run and the result is marked "partial": a score from the tests that ran (shown only when both halves have at least one test), but no level. A level needs every scored test. Tests you left out are not counted in the completion rate.
  • A processor marked "Results don't match" never counts. If no processor matches, that test gets the floor score of 1.
  • The AI multitasking test and Google-managed AI features are shown beside the score, not in it.

Levels: Basic (under 1200), Capable (1200-2399), Advanced (2400-4799), Flagship (4800-9599) and Cutting-edge (9600 or more): each level starts at twice the score of the one below, and the reference phone (6000) is Flagship. A capped result is at most Capable; partial results (a scored test left out) get no level.

Known limitations and design choices

  • What "correct" means: consistency with the CPU within per-test tolerances (see Answer checks), with the CPU checked against a PC reference. A mistake shared by the CPU and an accelerator would pass where no PC reference or quiz covers it.
  • Test sets are small and fixed: 14 photos, 9 detection photos, 7 sound clips, 4 speech recordings, 8 style pictures (4 photos × 2 paintings) and 3 quiz questions. They ship with the app, are pinned by SHA-256, are the same on every phone and change only with a new suite version; they are not rotated. They were chosen for clear answers, not for difficulty or class balance: the test checks that processors run models correctly, not how accurate the models are.
  • What is timed: the time for one input (latency) for photos, objects, sounds, image style and the speech encoder; word pieces per second for speech text output; tokens per second (prompt and answer) for the chat model. Medians of many timed runs after a warm-up; load and compile time is recorded but not scored. Throughput and real-time factor are not measured.
  • How tests combine: each test scores against the reference phone (1000 = equal); a test with two model families (photos) or two speeds (speech, chat) takes their geometric mean. The six tests have equal weight and are added up (Recognition + Generative). No log compression: a test where an accelerator makes a phone much faster adds a lot to its score.
  • Small, stable models: models were chosen to finish and agree on as many phones as possible. Such models suit mid- and low-range phones well and show less of the differences between high-end phones on large generative models.
  • The chat test is one 1B-class offline language model (Gemma 3 1B, 4-bit): it shows how fast a phone runs a small offline language model, not larger models, long contexts, tool use or general "generative AI intelligence". It is long and needs a lot of memory, so phones with little memory can end "partial".
  • Hardware plus software openness: each test uses the best processor an ordinary app can reach. NPU access depends on the chip maker (Snapdragon through Qualcomm's libraries; MediaTek Dimensity 7300, 8300 and 9000 to 9500 through NeuroPilot; Pixel and some Exynos through NNAPI; other MediaTek and other Exynos not yet open to the app), so a ranking reflects the chip and how open its NPU is, and the vendor's driver and runtime versions on the phone. A processor that cannot run a model is skipped, never scored. Every phone gets the same model files and quantisation; there are no per-chip model builds, except that the chat model also runs in Google's AI-processor build on the chips that have one.
  • No test is a trial now. Image style was a trial before suite version 3 and is scored since app 0.3.9, with the same weight as the other tests.
  • Heat, room temperature and charging affect results. They are recorded (battery temperature, thermal state, power source) and shown, and charging is marked, but they cannot be removed. Background apps and free memory are not controlled beyond the app's own work (no ads or network during a run).
  • The AI multitasking test is qualitative and measures neither power nor energy. It is shown beside the score, never in it.

Fairness rules and versioning

Every change to the method, newest first, is listed in What changed.

  • Same inputs everywhere: models, photos and prompts are fixed and pinned by SHA-256. Scores are compared only within the same suite version. Since app 0.3.11 every report also records one SHA-256 fingerprint over all bundled models and test inputs, computed on the phone from the installed app, and whether it equals the suite's pinned value; the downloaded chat and speech models are checked against their own pinned SHA-256 before use.
  • Nothing else runs during a test: no ads load or refresh and no network work happens until the run ends.
  • Same power state: results are compared only with runs in the same power state (on battery or charging). Since app 0.3.10 a score measured while charging (at the start or end of the run) is marked "Charging" next to the score, because the reference phone is measured on battery.
  • What the score measures: the AI speed that ordinary apps can reach on the phone, not the chip's peak. Some AI processors are closed to apps or reached only through Android's older NNAPI route, so a phone can score below what its chip could do with the maker's own tools. A processor that apps cannot use is reported as not available, never estimated. NNAPI is deprecated: if a phone update removes its driver, that phone's AI processor drops out of the score, and the app shows this rather than hiding it.
  • Honest fallbacks: a processor the phone does not offer is skipped, never scored. Suspected CPU fallbacks are flagged.
  • Model downloads: the optional chat and speech models are downloaded once (the chat model through Google Play, after the user agrees to the Gemma terms), ahead of the run, and checked against its pinned SHA-256 before use.
  • New suite version: any change to models, inputs, settings, runtime versions (LiteRT, LiteRT-LM, Qualcomm QNN) or the formula raises the suite version, and the reference phone is measured again. A formula change that earlier results can be recomputed with, from their stored test scores, keeps the suite (the summed score of app 0.3.18). Suites 3 to 5 run on LiteRT 2.3.2, LiteRT-LM 0.18.0 and QNN 2.51.0; each score records its suite and runtimes.
  • Suite 4 (app 1.0.4): the CPU uses one thread per fast core, 4 to 8, instead of 4 on every phone, so phones with more fast cores are not held back. Each report records the cores, the fast cores and the threads used, and the run screen shows them ("CPU · 6 cores used"). The reference phone has 4 fast cores, so it runs exactly as in suite 3 and its reference values stand. Suite 3 and suite 4 scores are not compared.
  • Suite 5 (app 1.0.14): the chat model is Gemma 3 1B (4-bit, Google, Gemma Terms of Use) on every phone instead of Qwen3 1.7B, so chat results compare across chips; on chips with a Google AI-processor build of the same model the chat test also runs on the AI processor. The chat reference was measured on the reference phone on battery (median of 3 runs with release 1.1.0, in the score since app 1.1.4); chat results from earlier suites are not comparable.
  • The AI multitasking test is versioned separately from the score suite. A change to it is listed in What changed and does not change the suite version or the score.
